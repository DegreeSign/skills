# i18n and language

## Source of truth

- The translation source file is the single source of truth. Always edit it, never the generated files.
- Never run the translate command. It is reserved for the final build and is run manually by the user.
- Every translatable string has a key in the source file.
- If a key is missing at runtime, it is missing from the source file. Add it there, never patch a generated language file.
- Types are derived from the source file and the translation accessor is typed from those types. Never hardcode key unions and never pull keys from generated files.
- Generated files (a combined language file, a timestamp file, and per-language bundles) are build output. Never read them to resolve or validate keys.
- Never use a fallback value for a translation key (`key || 'default'`). If the key exists it has a value; if it does not, fix the source file.

## Key naming

- Keys must match the exact text for short strings (one to three words), never prefixed or lowercased. A single-word value uses that word as its key.
- Only texts longer than three words may use a descriptive key.
- Keys differing only by case are distinct keys.
- Key names must describe their content, never carry an arbitrary numeric suffix.
- Meaningful namespaces and semantic codes are allowed. Meaningless legacy prefixes are not.
- Never store all-caps text. Store title or sentence case and apply uppercase with CSS. Acronyms are exempt.
- Never use layout or presentational jargon in a key (`eyebrow`, `section`, `column`, `wrapper`). Name the content instead.
- When adding a key, derive it from the content it labels and re-check it against every rule above.

## Using translations

- Auto-translation replaces `innerText` on every element whose `data-txt` attribute matches a key. Give translatable elements `data-txt="key"` with the default text in the markup.
- Never use an `id` for translation. An `id` is for selection and hooks only.
- Never add `data-txt` to an element whose text is set from code elsewhere. Leave that text to code reading the translation accessor.
- For dynamic content, import the translation accessor and read the key from it.
- Never put `data-txt` on a container or button whose children are populated dynamically. Auto-translation wipes all child nodes of the element it targets. Put `data-txt` on the leaf text element only.
- Keys meant only for code reads must never be reused as a `data-txt` value.

## Placeholders

- Placeholders use zero-based positional tokens (`{0}`, `{1}`), replaced in code.
- A placeholder must sit mid-string, never at the very start or end. If it is required at an edge, build the string in code with a template literal instead of a key.
- Use template literal interpolation for values that interpolate into strings built in code, never `+`.

## Keep hardcoded

Never add these to the source file. Keep them hardcoded:

- Single characters (`+`, `-`, `*`, `#`).
- Emojis.
- Single-letter labels (`E`, `N`).
- Currency symbols.
- Formatting separators (` | `, ` - `, newlines).
- Image sizes (for example `256x256 JPG`).
- Example or placeholder values (for example `https://`).

Image `alt` text is translatable: give `<img>` elements `data-txt` with the English default in `alt`, exactly like other translatable elements. Never add `data-txt` to an image whose `alt` is assigned from code; that keeps its dynamic text.
